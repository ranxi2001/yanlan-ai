# 言澜追平飞书妙记：样本复盘、开源对照与补齐计划

调研日期：2026-09-08。代码基线：`4892507a7c9c0606c335f31e0be0be704372f2c8`，package 版本 `0.6.2`。

本文是产品与工程改造方案。开源项目已核对公开文档和下列关键源码。下方任务状态保留计划建立时的快照；最新实现与真实音频结果见[美团逐字稿实测报告](meituan-transcript-live-test-2026-09-09.md)。本文所有验收数值均为拟定目标，不是言澜当前成绩，也不是飞书的实测成绩。

## 1. 结论与目标边界

言澜当前最突出的短板是：摘要被最终提交机制压缩成原话拼接、对话缺少可靠的话轮和说话人结构、一般语义错词不能被现有质量门充分发现。术语识别有局部优势，证据追溯也已具备基础，但这些优势尚未转化为可以直接阅读和复用的纪要。

优先借鉴五个项目的不同能力，而非整体替换言澜：

| 参考项目 | 借鉴重点 | 对应言澜改造 |
| --- | --- | --- |
| WhisperX | VAD、强制对齐、把说话人时间段映射到词和片段 | 音频处理块与阅读句子分开；增加真实对齐时间 |
| pyannote.audio | 整场说话人分离、人数约束、时间区间输出 | 跨块稳定匿名说话人，允许未知和重叠 |
| FunASR | 中文 ASR、VAD、标点、时间戳、说话人组件、热词组合 | 中文技术会议的备选语音管线与音频复核基线 |
| Meetily | 分块概括、合并概括、按模板生成报告 | 从原话摘录升级为带证据的语义总结 |
| anarlog（原 Hyprnote 仓库入口） | 逐字稿与笔记分离、可编辑摘要、独立选择转写与总结服务 | 原始稿、修订稿、阅读稿、纪要分别版本化 |

“追平”分两层，分别验收：

1. **核心内容体验**：在同一批中文录音上，转写、说话人、定位、摘要、检索和导出达到飞书妙记相当水平。这是本计划的优先目标。
2. **协作产品体验**：共享权限、评论、版本、多人协作、任务与文档集成。这是后续产品范围，不能因一份纪要质量改善就宣称全面追平。

保留言澜已有的 BYOK、浏览器录音、恢复、术语账本、受控 Agent 和来源校验。新增能力通过清晰接口接入，不要求浏览器用户默认运行整套 Python/GPU 服务。

## 2. 证据范围与样本结论

样本：飞书导出的 [逐字稿](../美团infra飞书妙记逐字稿.md)（原文件名为transcript.md）；言澜导出的 [美团 / Agent Infra / AI Infra 会议纪要](<../美团 - Agent Infra - AI Infra会议纪要.md>)。两者的内容与时序对应同一场约 25 分钟的面试。

- 飞书文件提供逐字稿，不含其 AI 摘要。不能从这两份文件直接比较两家的摘要质量。
- 本次没有回听这场面试音频；飞书逐字稿是参考稿，不是人工金标准。
- 导出文件不能证明当次使用的 ASR 参数、是否执行了术语校正、是否走了降级路径，也不能证明运行版本等于当前代码。下面区分产物观察与当前代码机制。
- 仓库另有云原生周会音频，它不是本次面试音频，不能替代本样本做声学验收。
- 文件创建时间是导出元数据，不能拿它解释录音中“还有一个月”的相对时间。

### 2.1 可直接观察的差距

| 维度 | 飞书样本 | 言澜样本 | 结论 |
| --- | --- | --- | --- |
| 时间片段 | 64 个带时间片段 | 51 个片段，起点从 00:00 到 25:00，按 30 秒递增 | 言澜呈现的是固定块边界，未充分还原语义边界 |
| 对话结构 | 问答多有分开，导出未附角色标签 | 所有片段标成“发言人 1”，多个片段混合提问与回答 | 本样本的说话人结构不可用；不能据此计算飞书 DER |
| 阅读负担 | 相对较少语气词与重复 | 大量“呃、嗯、然后”与口头重启 | 需要独立阅读稿，不能破坏原始记录 |
| AI 摘要 | 未提供 | 主要拼接 06:00、06:30、23:30 的片段 | 话题跳跃、断句、主要议题遗漏 |
| 金句 | 未提供 | “的更浓厚的兴趣…”“管，那你要说大了…”等整块引用 | 可定位不等于可作为金句 |
| 发言人总结 | 未提供 | 原文片段拼接，随后在要点中重复 | 既没分人，也没完成概括 |
| 标题 | “美团北斗3面 HRBP面” | “美团 / Agent Infra / AI Infra会议纪要” | 言澜标题缺少面试场景；“北斗3面”也不能仅凭飞书标题注入正文事实 |

### 2.2 高价值错误与局部优势

下表时间为对应区间，不代表经过音频对齐的精确词起点。

| 区间 | 飞书文本 | 言澜文本 | 处理原则 |
| --- | --- | --- | --- |
| 00:00 | 姓名、HRBP | “男性同学”“XBP” | 人名与职能身份进入高优先级复核；姓名可使用用户确认信息辅助 |
| 03:30 | “工作量” | “工作车辆” | 检查跨块断词，复核后修订，不能只做术语替换 |
| 09:30 | “风控的算法” | “分摊的算法” | 研究方向发生语义变化，应触发异常检测 |
| 13:30 | “量化策略” | “内审之类” | 存在实质分歧，待回听，不直接认定飞书正确 |
| 15:00 | “策略失效” | “审美失效” | 业务搭配异常，优先定点回听 |
| 15:30 | command / Commander | Kubernetes | 后文出现 Karmada，应检查是否同一贡献项目，不全局盲替换 Kubernetes |
| 17:30 | OKE / MOKO、Commander 等 | Volcano、Karmada | 言澜更符合技术语境；最终拼写仍需用户或音频证据确认 |
| 04:00 左右 | agent honey 等 | agent harness 等 | 言澜并非术语全面落后；其他产品名两边也有疑似错误 |

两份稿子都保留了不少经历与数值。当前主要问题之一是“原稿里有的信息没有进入摘要”，而不是整场音频内容都未识别出来。不能用分段数量推算识别准确率，也不能把更长的文本解释成更完整。

## 3. 当前代码根因

| 代码位置 | 已核实机制 | 造成的限制 | 改造要求 |
| --- | --- | --- | --- |
| `src/api.js:427`，`extractMeetingSummaryCandidates` | 提取提示要求完整摘要，但每批摘要原话仅 1～3 条 | 提取的完整概括没有成为最终摘要文本 | 保留概括候选及逐条来源，不只保留引用 |
| `src/api.js:584`，`buildMeetingEvidenceLedger` | 摘要记录主要保存 quotes、keywords、batch_index | 账本缺少主题与原子事实，后续难以评估信息遗漏 | 增加事实、主题、问答关系及说话人归属 |
| `src/agent/profiles/meeting-analysis.js:156` | Agent 只能选证据 ID，不能写 title/summary/keywords | Agent 无法完成最终自然语言综合 | 引入带来源的摘要提案与语义复核契约 |
| `src/api.js:959` | 用前三个关键词拼接标题 | 不能可靠表达会话性质和核心事件 | 生成标题并约束实体、场景、日期来源 |
| `src/api.js:997`、`:1027` | 发言人总结与摘要直接拼原话，按字符预算截断 | 断句、重复、信息压缩质量低 | 以句子和要点预算组织内容；超长时重新概括 |
| `src/api.js:935` 附近 | 验证每个批次摘要记录被选中 | 批次覆盖不代表主题/关键事实覆盖 | 单独验收事实与主题覆盖率 |
| `src/asr-quality.js` | 检查空结果、重复、字符/Token 密度 | “审美失效”这类流畅错词可能通过 | 增加实体冲突、语义异常、边界完整性信号 |
| `src/audio-stream-core.js`；`src/asr-pipeline.js` | 固定大小 PCM 块；质量不合格时再细分；保留原始与调和结果 | 音频传输边界不是说话人或句子边界 | 音频块继续服务传输，另建对齐、话轮与阅读投影 |
| `src/api.js:330`；`src/asr-pipeline.js` | 缺失说话人或精细时间时存在回退标签/时间处理 | 下游可能把默认值当已识别事实 | 显式记录来源、能力缺失与未知状态 |
| `src/api.js:1279`；`src/app.js` | 已有 interview 模式、上下文和面试报告 | 不能把本样本的通用导出解释为完全没有面试能力 | 补会话类型建议、面试复盘模板和模式迁移 |
| `src/api.js:2032` 起 | 已有阅读投影、片段处理能力 | 本样本仍未呈现干净话轮，现有投影不等于完整语义清理 | 在现有能力上增加可回放清理与来源跨度 |
| `scripts/meeting-agent-eval.mjs:27` 起 | 检查完成、证据、承诺分类和部分金标准数量 | 摘要非空、证据存在不能证明摘要好用 | 增加真实录音内容质量与盲评 |

关键设计调整：**原始音频和 ASR 记录保持不可变；后续对齐、分人、清理、概括可以生成可追溯的新版本。** “来源不可变”不应意味着“首次 ASR 的粗时间、错误角色与断句永久不可修复”。

## 4. 开源对照：可确认的实现与适用边界

以下均固定到本次读取的 commit，避免把未来的 README 当成本次依据。README 的性能宣传没有作为言澜收益预测。

### 4.1 WhisperX：对齐与分人是独立步骤

- [README](https://github.com/m-bain/whisperX/blob/2cfd7b7c5c7bba144954364db747319b50e8232b/README.md)给出 VAD、ASR、语言相关的强制对齐、说话人分离与词级说话人映射流程。
- [diarize.py](https://github.com/m-bain/whisperX/blob/2cfd7b7c5c7bba144954364db747319b50e8232b/whisperx/diarize.py)实现 `DiarizationPipeline` 和 `assign_word_speakers`，通过时间重叠关联说话人和文本单位，接受已知人数或人数区间。
- README 明确列出重叠语音、分人不完美、部分词无法对齐、需要语言相关模型等限制。

借鉴：把块级时间升级为有来源标识的词/句时间；在话轮变更处重新分句。不能仅把 30 秒改成 10 秒就声称定位问题已解决。中文夹英文、数字和项目名必须单独验收，不能将英文示例效果外推。

集成选择：先作为离线对齐候选与评测基线，不默认替换现有 ASR。若对齐输入采用 MiMo 文本，需验证字符集、文本清理与接口兼容性。代码为 BSD-2-Clause，依赖及模型权重分别核对。

### 4.2 pyannote.audio：匿名说话人不等于实名身份

- [README](https://github.com/pyannote/pyannote-audio/blob/b749285c5cdd4636b2edc7f766f1352c8dde9369/README.md)提供本地 `community-1` 管线、时间段和说话人输出，并列出分人错误率评测。
- 同页也包含商业 `precision-2`，不能把商业能力计作免费开源能力。
- 使用示例要求接受相应模型条件并获取模型访问凭证。工具代码 MIT 不代表所有模型采用同一许可证。

借鉴：先保证同一录音里的 `speaker_0`、`speaker_1` 稳定，再由用户确认“候选人/面试官”。无法判断的短应答保留 unknown；重叠区间保留多说话人信息。不能用内容猜测冒充声学分离。

集成选择：通过可选本地伴随服务或用户配置的处理服务返回时间段。双音轨录音应优先利用实际音轨来源，但仍需处理串音和回声，不能假设两个音轨天然百分之百对应两个人。

### 4.3 FunASR：中文语音管线可组合

- [README](https://github.com/modelscope/FunASR/blob/130e57a6fdb9661e2b0cc59199fb31ef81f2b9e9/README.md)给出 Paraformer、FSMN-VAD、ct-punc、CAM++ 的组合示例及 hotword 参数。
- [auto_model.py](https://github.com/modelscope/FunASR/blob/130e57a6fdb9661e2b0cc59199fb31ef81f2b9e9/funasr/auto/auto_model.py)包含 VAD 片段、标点与文本表面形式映射、时间戳组织等实现。
- README 区分流式模型与离线模型，也说明部分说话人结果来自组合管线，并非基础 ASR 模型原生能力；标签是录音内匿名索引。

借鉴：中文标点恢复、热词、VAD、说话人聚类分别验收。建立 MiMo 与 FunASR 的同音频对照，判断是否用作主转写、疑难复核或私有部署选项；先测再选。后处理热词替换不能视作声学证据。

集成选择：新增 provider 能力声明，分别注明流式、词时间、说话人、热词支持。代码 MIT，权重按模型卡独立核对。本次不采用 README 的相对 CER 宣传数字作为收益依据。

### 4.4 Meetily：摘要需要综合步骤

- [processor.rs](https://github.com/Zackriya-Solutions/meetily/blob/0281737d87d26352fb0adc78c8c0975f691b23d1/frontend/src-tauri/src/summary/processor.rs)包含分块概括提示、合并概括提示及最终模板报告提示；分块支持重叠并尝试在句/词边界切分。
- [defaults.rs](https://github.com/Zackriya-Solutions/meetily/blob/0281737d87d26352fb0adc78c8c0975f691b23d1/frontend/src-tauri/src/summary/templates/defaults.rs)明确包含 `daily_standup`、`standard_meeting` 内置模板。
- [README](https://github.com/Zackriya-Solutions/meetily/blob/0281737d87d26352fb0adc78c8c0975f691b23d1/README.md)区分社区版与 PRO；其中说话人能力仍以 PRO 计划/Coming Soon 描述，不能按日期推断已经交付。源码中有模板基础设施，也不能据此认定 PRO 的全部自定义工作流都在社区版可用。

借鉴：分批事实提取后再综合成可读报告，支持场景模板。言澜应保留自己的逐条证据和承诺校验，并补充语义支持检查；概括的概括容易丢条件或归属，不能只把多级摘要链复制过来。

该版本处理器含先生成英文再处理目标语言的逻辑，不适合原样用于中文优先的言澜。采用中文直接综合，降低翻译导致的实体漂移、延迟与成本。

### 4.5 anarlog：笔记与逐字稿是不同资产

- 原 `fastrepl/hyprnote` 入口本次重定向到 [fastrepl/anarlog](https://github.com/fastrepl/anarlog/blob/3c55a43b55b9cc8bb80f2a9711605b7bd2481e53/README.md)。README 明确当前团队另做 char，而本仓库社区应用仍维护；不将两者当作同一代码库。
- 文档说明转写与 Intelligence 可独立选择，逐字稿、笔记保存在本地 SQLite，摘要可编辑并导出 Markdown。
- [enhance.system.md.jinja](https://github.com/fastrepl/anarlog/blob/3c55a43b55b9cc8bb80f2a9711605b7bd2481e53/crates/template-app/assets/enhance.system.md.jinja)包含摘要输出及技术名词保留要求。
- [enhance-validator.ts](https://github.com/fastrepl/anarlog/blob/3c55a43b55b9cc8bb80f2a9711605b7bd2481e53/apps/desktop/src/store/zustand/ai-task/task-configs/enhance-validator.ts)检查标题与模板开头等格式；该文件本身不是完整事实验证器，不能据此证明整套产品没有其他验证。

借鉴：原文与增强笔记独立保存，编辑后的笔记有自身版本；重新生成前保留人工修改。言澜现有来源追溯应延伸到编辑、重新分析、分享和导出，而不只是生成时。

社区应用为 MIT，`enterprise/` 为商业许可范围。本文仅借鉴社区实现与文档中确认的能力。

### 4.6 飞书妙记：产品基线而非内部架构依据

本次读取的[飞书官方介绍](https://www.feishu.cn/content/article/7578773484596153570)公开描述了转写、发言人区分、时间轴、标题/总结、关键词定位、编辑、评论、导出与片段分享。

这些是产品能力声明，不是本次实验结果。页面中的“98%”等宣传数字没有对应本评测语料和归一化口径，不能直接作为准确率金标准。实名映射和协作还可能依赖平台参会信息，不能把混合音轨上的匿名分人与平台实名识别等同。

## 5. 建议的数据与处理契约

### 5.1 分离五类版本化资产

| 资产 | 内容 | 修改规则 |
| --- | --- | --- |
| 原始记录 | 音频引用、音轨、raw ASR、provider 原始时间和标签 | 不覆盖；记录 provider、参数和音频哈希 |
| 声学注释 | VAD、对齐区间、匿名说话人、重叠信息 | 新增版本，明确来源为 provider/alignment/estimated/unknown |
| 修订逐字稿 | 经证据或人工确认的词语修订 | 最小修改、保留 correction ledger，可重放 |
| 阅读稿 | 标点、去冗余、按句/话轮组织 | 每段映射多个原始跨度；不冒充原始逐字稿 |
| 纪要 | 主题、问答、摘要、金句、决定、后续安排 | 每条概括有证据；用户编辑与机器生成版本分开 |

新增字段应采用下一版 schema 迁移方案，并兼容当前 `publicMeeting`、Markdown/SRT/分享页。旧版缺失的分人、对齐信息标记 unknown，不根据已有“发言人 1”推断真实单人。

建议摘要要点结构（设计草案，未实现）：

```json
{
  "id": "claim-01",
  "text": "HR 说明，自研与开源模型并用，传统搜广推与大模型并行。",
  "topic_id": "team-model-application",
  "attribution": { "role": "interviewer", "status": "reviewed" },
  "evidence_ids": ["evidence-22m-model-mix", "evidence-22m-parallel"],
  "support_status": "supported",
  "source_revision": "transcript-revision-id"
}
```

证据记录另外保存 `source_segment_id`、字符跨度和音频区间。若只有块级时间就只能提供近似定位；不以字符等分产生的时间冒充强制对齐结果。角色未经确认时保留未知或候选状态。

### 5.2 将可信校验拆成两类

**确定性校验**负责 ID、来源哈希、字符跨度、时间合法性、版本一致性、引用原文、原子提交与预算。它能证明“来源对应”，不能仅靠字符串或数字出现证明“概括受来源支持”。

**语义校验**检查每条概括的主体、谓词、否定、条件、时间、数值、归属和问答关系。复核器读取概括和原始上下文，不只读取上一层摘要；模型复核结果也不是数学证明，需要人工金标准持续校准。

当复核失败：修订或删除具体要点并显示部分结果状态。摘要服务不可用时可以提供明确标注的“原文摘录”，不将其伪装为完成的 AI 摘要。决定、任务保留更严格的承诺分类，不因更换摘要机制而放宽。

### 5.3 从块覆盖改为事实覆盖

1. 输入仍使用有界批次，但按话轮/主题边界切分，边界携带上下文重叠和原始 ID。
2. 每批提取原子事实、提问、回答、纠正关系、未决事项及原话证据，不能只选 1～3 个泛化摘录。
3. 全局聚合主题，同实体的冲突事实并存并标记，不悄悄取最后一句。
4. 按场景生成摘要；对重要但未纳入摘要的事实保留覆盖检查记录。
5. 最终检查覆盖、归属和矛盾。超过预算时优先压缩次要主题，不按数组奇偶丢批次或截断半句话。

### 5.4 阅读稿、说话人与会话模式

- 阅读清理优先处理语气词、口头重启和相邻重复，必须保留“可能、应该、不是、并行、至少、大约”等限定。每个 edit 有前后文本、来源与原因。
- 声学分人与角色映射分开；不能按 30 秒块或每次 API 调用重新编号。实时结果允许 provisional，会后整场聚类产生 final 并保留映射历史。
- 当前面试模式侧重辅助报告，还需“候选人复盘/信息整理”模板。模板提供经历、主要问答、团队信息、后续安排，不强行生成候选人评分。
- 系统可建议场景，用户能切换。已有录音切换模板时复用逐字稿，不要求重新转写。
- 金句要求完整、单一归属、脱离上下文仍可理解；跨块引用可由多个连续来源跨度支撑。宁可无金句，也不把半句话或问答混合块发布成金句。

## 8. 评测方案与追平判据

### 8.1 语料与实验控制

第一轮建议至少 30 段真实录音，覆盖双人面试、多人大组会、中文夹英文术语、远场噪音、短应答/打断、60 分钟以上长会议；分层标签可重叠，每类至少 5 段。每类划分开发与盲测样本，同一会议及其切片不得跨集合。保留本次面试为回归样本，不只在它上面调参。

由两位标注者回听建立原始逐字稿、话轮、关键实体、事实和摘要要点，分歧经裁决。脱敏公开文本 fixture；私人音频的公开另走明确发布授权，日常研究和日志不上传整段私人文本到代码搜索服务。

所有系统处理相同输入音频，记录版本、语言设置、热词、说话人数提示、运行模式、硬件、时间、费用。基础条件统一；带用户热词/姓名提示的辅助模式单独比较，不能只给言澜额外信息却报告为同条件胜出。

本次未取得飞书的同音频摘要、说话人完整导出及延迟记录，这些是后续实验输入。当前只形成基线设计，不填造结果。

### 8.2 拟定质量门

以下阈值用于启动项目，先冻结口径，再在开发集验证可行性；修改阈值须留版本记录，不能根据盲测结果临时降低标准。

| 指标 | 口径 | 首轮目标 / 与飞书比较 |
| --- | --- | --- |
| 中文 CER | `(替换+删除+插入)/参考字符数`；去标点、空白，数字/大小写等规则固定 | 盲测整体不高于飞书；报告逐场宏平均与总体微平均 |
| 英文技术词错误 | 独立实体/英文 token 清单，不能只依赖中文 CER | 与飞书逐项配对，不能被大量普通汉字稀释 |
| 关键实体准确率 | 人名、岗位、项目名、数量、日期的 mention 级精确率/召回率 | 清晰录音目标 ≥95%；实体误改率单列，不靠“全不改”获得好分 |
| DER | `(漏检语音+误检语音+说话人混淆时长)/参考说话时长`；固定 0.25s collar，计入重叠，另报非重叠子集 | 清晰双人目标 ≤10%；有可用飞书标签时做同口径比较 |
| 角色归属错误率 | 已标注事实被归给错误角色的比例，另报 unknown 比例 | 清晰双人目标 ≤2%；unknown 不能从覆盖率分母中消失 |
| 句起点定位误差 | 相对于人工句起点的绝对秒差，报告 median/p95 和可对齐覆盖率 | 清晰语音 p95 ≤1.5s，可对齐覆盖 ≥95%；不可对齐项计入失败统计 |
| 关键事实覆盖率 | 人工关键事实中被纪要正确覆盖的权重占比；权重评测前冻结 | ≥90%，本样本 F01～F14 在完整纪要中全部覆盖或明确标注疑点 |
| 摘要事实支持率 | 每个可核查概括是否被源上下文支持，由人工复核 | ≥98%，严重错误为 0；不把候选人自述当外部证明 |
| 来源有效性 | 引用 ID/跨度/时间/版本均合法且可解析 | 100%；另查语义支持，不能只检查存在性 |
| 阅读完整性 | 盲评句子完整、角色明确、重复适当、没有误删限定词 | 5 分制平均 ≥4；固定否定/条件/问答挑战集语义破坏为 0 |
| 决定与行动项 | 按人工标注计算 precision/recall；区分确定承诺、意向、后续安排 | 严重虚构为 0，precision ≥98%，同时报告 recall 防止全部输出“无” |
| 处理效率 | 首段延迟、录音结束到最终稿、失败率、音频 RTF、每小时费用 | 先测基线；清晰 25 分钟样本会后处理目标 ≤5 分钟，固定硬件/网络口径 |
| 综合盲评 | 隐去品牌，随机左右顺序；至少两名评审，保留平局，按录音配对 | 言澜胜出+持平 ≥80%，同时通过关键质量门 |

严重错误包括：问句变事实、否定反转、说话人错归导致立场反转、凭空产生录用结论、虚构任务负责人或截止日、将收益自述改成保证收益。任何一个严重错误都应阻止对应版本被宣称达标。

CER 比较必须使用同一种转写模式。若一个系统默认清理口语，应另设内容保真/阅读稿评测，不能拿清理后的稿子对保留所有语气词的原始金标准计算 CER 后直接判差。

30 段是首轮最低规模，不足以证明对所有行业全面等效。报告配对差值、按录音 bootstrap 的 95% 置信区间和各场景结果；如果区间仍支持明显劣化或某个关键场景失败，结论只能是“局部达到目标，继续扩样”。“内容追平”至少要求这些门槛在冻结盲测集达标，不以 README 功能数量认定。

### 8.3 评测拆分与诊断

1. **ASR 固定后测摘要**：统一人工逐字稿输入，比较当前拼接机制与新的摘要机制，隔离语音误差。
2. **摘要固定后测语音**：统一下游摘要配置，比较 MiMo、候选开源管线、校正开关、分人开关。
3. **端到端对飞书**：相同音频分别生成完整产物，比较人工修订耗时与盲评。
4. **回归挑战集**：至少包含问句→纠正、否定决定、条件计划、未知人名、Kubernetes/Karmada 共存、数字限定、跨块半句、重叠语音、长会末尾关键结论。

扩展现有 eval 输出：`audio/transcript hash`、代码/模型/参数版本、各阶段用时和费用、fallback 原因、unknown 比例、主题覆盖、支持率、严重错误数。trace 仍保存有界元数据；音频与完整文本保存在明确的数据资产中，不混入运行日志。

## 9. 发布、迁移与风险处理

- 用能力开关分别上线新摘要、阅读清理、对齐和分人，A/B 中一次尽量只改变一个主要因素，能够回滚到旧版资产。
- 修改逐字稿或说话人后，使旧摘要标记过期；异步任务提交必须校验 source revision，不能把旧结果覆盖新编辑。
- 新字段贯穿 `publicMeeting`、页面、分享、Markdown 和 SRT。断网、刷新、取消、provider 不支持和局部失败要进入现有恢复测试。
- 服务端语音能力是可选增强。首次配置时清楚说明处理位置；仅接入已经选择的 provider，不静默把原本本地保存的音频转发到其他服务。
- 不直接搬运模型宣传速度。Windows CPU/GPU、模型下载体积、冷启动与网络时间分别报告；开源替代只有在本语料收益和运行成本都可接受时才成为默认。
- 纯文档阶段不运行付费模型或下载大模型。进入实现后运行相关单测、真实语料 eval、浏览器/导出回归及仓库要求的 `npm run check`；一次成功示例不能替代这些验收。

## 10. 与既有架构文档的关系

[既有竞品与架构调研](competitive-architecture.md)保留了 Harness、受控工具、不可变来源和语音组件可替换的正确方向。本次补充两点具体修正：
